## 第零章 入门铺垫 —— 理解MySQL的基础概念

### 为什么要先学这个？

在学习具体问题之前，我们需要先建立一个整体认知。这就像盖房子要先打地基，地基稳了，后续的知识才能理解得更好。

#### 0.1 什么是MySQL？

**一句话定义**：MySQL是一个「**开源的关系型数据库管理系统**」。

我们来拆解这句话：

1. **开源（Open Source）**：源代码是公开的，免费使用。由瑞典MySQL AB公司开发，后被Oracle收购。

2. **关系型（Relational）**：数据以「表」的形式存储，表与表之间可以有关系。
   ```
   学生表（student）：
   ┌─────┬──────┬──────┐
   │ id  │ name │ age  │
   ├─────┼──────┼──────┤
   │ 1   │ 张三 │ 20   │
   │ 2   │ 李四 │ 21   │
   └─────┴──────┴──────┘

   成绩表（score）：
   ┌─────┬──────┬─────┐
   │ sid │ sid  │score│
   ├─────┼──────┼─────┤
   │ 1   │ 1    │ 90  │
   │ 2   │ 1    │ 85  │
   └─────┴──────┴─────┘
   ```

   可以通过sid关联学生和成绩，这就是「关系」。

3. **数据库管理系统（DBMS）**：管理软件，提供增删改查等功能。

#### 0.2 MySQL的存储引擎

MySQL最大的特点是「**插件式存储引擎**」。也就是说，MySQL支持多种存储引擎，像电脑的显卡一样可以插拔。

```
常见存储引擎：
┌────────────────┬──────────────┬────────────────────┐
│ 存储引擎       │ 特点         │ 适用场景           │
├────────────────┼──────────────┼────────────────────┤
│ InnoDB         │ 支持事务、行锁 │ 默认，推荐        │
│ MyISAM         │ 不支持事务     │ 只读、静态表      │
│ Memory        │ 存在内存中     │ 临时表、高速缓存  │
│ Archive        │ 压缩存储      │ 日志、归档        │
└────────────────┴──────────────┴────────────────────┘
```

**查看当前使用的存储引擎**：
```sql
SHOW ENGINE \G
-- 或者
SELECT ENGINE FROM information_schema.TABLES WHERE TABLE_NAME = 'user' \G
```

#### 0.3 为什么MySQL需要学习？

```
互联网公司数据存储方案：
┌─────────────────┐
│ 热数据 → MySQL   │ ← 需要高速读写
│ 温数据 → Redis  │ ← 缓存热点
│ 冷数据 → 磁盘   │ ← 归档存储
└─────────────────┘
```

大部分应用的「核心业务数据」都存在MySQL里。不会MySQL，寸步难行。

### 2. MySQL的架构是什么样的？

#### 2.1 四层架构图解

```
┌─────────────────────────────────────────────────┐
│           连接层（Connectors）                    │
│  JDBC、ODBC、Python连接等                        │
└──────────────────────┬──────────────────────────┘
                       │
┌──────────────────────▼──────────────────────────┐
│             服务层（Server Layer）               │
│  ┌──────────┬──────────┬──────────┬──────────┐ │
│  │ 连接管理 │ 缓存查询 │ SQL解析  │ SQL优化  │ │
│  └──────────┴──────────┴──────────┴──────────┘ │
└──────────────────────┬──────────────────────────┘
                       │
┌──────────────────────▼──────────────────────────┐
│             存储引擎层（Storage Engines）          │
│    InnoDB │ MyISAM │ Memory │ Archive             │
└──────────────────────────────────────────────┘
                       │
┌────────────────────▼────────────────────────────┐
│               物理文件层                        │
│   *.frm（表结构）│ *.ibd（数据）│ *.MYD│ *.MYI│
└──────────────────────────────────────────────┘
```

#### 2.2 各层职责

**1. 连接层**
```
负责：建立连接、权限验证、连接池管理
```
- 处理连接请求
- 验证���户名密码
- 管理连接池

**2. 服务层**
```
负责：SQL解析、优化、执行
```
- SQL解析：把SQL语句变成数据库能认识的形式
- 查询缓存：之前查过的结果可以直接返回（MySQL 8.0已移除）
- SQL优化：选择最快的执行路径
- 执行：调用存储引擎获取数据

**3. 存储引擎层**
```
负责：数据的存储和读取
```
- InnoDB：默认，支持事务
- MyISAM：不支持事务全文索引
- Memory：内存存储

**4. 物理文件层**
```
负责：数据落盘
```
- .frm：表结构定义
- .ibd：InnoDB的数据和索引
- .MYD：MyISAM的数据
- .MYI：MyISAM的索引

#### 2.3 SQL执行流程

```
SQL语句 → 连接层 → SQL解析 → 优化器 → 存储引擎 → 返回结果

详细流程：
1. 客户端发送SQL
2. 连接器检查权限，建立连接
3. 查询缓存（如果有结果直接返回）
4. 解析器解析SQL，生成解析树
5. 预处理器验证字段、表存在
6. 优化器选择索引，制定执行计划
7. 执行器调用存储引擎
8. 存储引擎读取数据
9. 返回结果给客户端
```

#### 2.4 回答模板

> MySQL整体采用四层架构：
>
> 1. **连接层**：负责处理客户端连接、管理连接池、验证权限。常见的JDBC、Python connector都在这一层。
> 2. **服务层**：包括SQL解析、查询缓存（8.0前）、SQL优化、执行器。SQL优化器会选择最优的执行路径，比如用哪个索引、要不要走索引覆盖等。
> 3. **存储引擎层**：这是MySQL最特色的地方，采用插件式架构。最常用的是InnoDB，支持事务和行级锁；MyISAM不支持事务但查询快，各有特点。
> 4. **物理文件层**：实际的数据文件，如.frm表定义、.ibd数据文件等。
>
> 一条SQL的执行流程是：客户端发送SQL → 连接器建立连接 → 解析器解析SQL → 优化器选择执行计划 → 执行器调用存储引擎 → 返回结果。

### 3. MySQL有哪些存储引擎？有什么区别？

#### 3.1 四大存储引擎对比

| 特性 | InnoDB | MyISAM | Memory | Archive |
|------|-------|--------|--------|---------|
| **事务** | 支持 | 不支持 | 不支持 | 不支持 |
| **锁机制** | 行锁 | 表锁 | 表锁 | 行锁 |
| **外键** | 支持 | 不支持 | 不支持 | 不支持 |
| **全文索引** | 5.6+支持 | 支持 | 不支持 | 支持 |
| **存储限制** | 64TB | 256TB | 受限于RAM | 无限制 |
| **缓存** | 数据和索引 | 只有索引 | 内存 | 压缩存储 |
| **MVCC** | 支持 | 不支持 | 不支持 | 不支持 |

#### 3.2 InnoDB vs MyISAM 详细对比

**InnoDB（默认，推荐）**
```
适用场景：
  - 需要事务支持
  - 并发写入多的业务
  - 数据更新频繁的场景
  - 需要行级锁

特点：
  - 支持ACID事务
  - 支持行级锁
  - 支持外键
  - MVCC多版本并发控制
  - 自动崩溃恢复
```

**MyISAM（老项目可能还在用）**
```
适用场景：
  - 以查询为主，写入很少
  - 不需要事务
  - 表很小，主要是读
  - 需要全文索引（老项目）

特点：
  - 查询速度快（不带事务开销）
  - 全文索引完善
  - 锁粒度是表锁
  - 崩溃后无法恢复
```

**血的教训**：
```
曾经有一个项目用了MyISAM引擎，
某天服务器突然关机重启，
数据文件损坏，无法恢复！
从此坚决用InnoDB！
```

#### 3.3 存储引擎的选择

```sql
-- 创建表时指定引擎
CREATE TABLE user (
    id INT PRIMARY KEY,
    name VARCHAR(50)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 修改已有表的引擎
ALTER TABLE user ENGINE=InnoDB;
```

**选择建议**：
```
✓ 99%的场景用InnoDB
✓ 只有纯读、不需要事务的报表表可以用MyISAM
✓ 临时表用Memory（重启丢失）
✓ 大日志用Archive（只增不减）
```

#### 3.4 回答模板

> MySQL支持多种存储引擎，最常用的有四种：
>
> 1. **InnoDB（默认，推荐）**：支持事务和行级锁，适用于绝大多数场景。它采用MVCC多版本并发控制，支持高并发。数据储存在.ibd文件中，崩溃后可以自动恢复。是我们公司的默认选择。
> 2. **MyISAM**：查询快但不支持事务，只有表锁。适合那些以读为主、基本不更新的静态表，老项目可能还在用，但我们已经不用了。
> 3. **Memory**：存在内存中，重启后数据丢失。适合做临时表或高速缓存。
> 4. **Archive**：专为大写少读多的场景设计，压缩存储。
>
> 一般情况下无脑选InnoDB就够了，除非有特殊需求。

## 第二章 索引与查询优化（高频 ★★★★★）

### 4. 什么是索引？为什么要用索引？

#### 4.1 索引的概念

**一句话解释**：索引就像书的目录，可以快速找到目标，不用一页一页翻。

```
无索引：全表扫描
  SELECT * FROM user WHERE name = '张三';
  → 从第一行开始，一行一行比对
  → 100万行 → 100万次IO

有索引：索引查找
  CREATE INDEX idx_name ON user(name);
  → 索引树 → 直接定位
  → 100万行 → 约20次IO
```

#### 4.2 为什么用索引？

**性���提升**：几百上千倍！
```
- 没有索引：O(n) 全表扫描
- 有索引：O(log n) 索引查找
- 主键索引：O(1) 直接定位
```

#### 4.3 索引的代价

```
代价1：占用空间
  - 索引也是数据，要占磁盘空间
  - 几百万条的表，索引可能比数据还大

代价2：降低写操作性能
  - INSERT/UPDATE/DELETE时要维护索引
  - 索引越多，写入越慢

代价3：不一定有用
  - 基数低的列（性别）不适合建索引
  - 查询不到索引 = 白建
```

#### 4.4 回答模板

> 索引是一种数据结构，用于加速数据查找。它的作用类似于书的目录，可以通过它快速定位到目标行，而不需要逐行扫描。
>
> 为什么要用索引？因为查询性能可以提升几百上千倍。没有索引的查询是全表扫描，有索引的查询是直接定位。在百万级数据量下，这个差距是质变的。
>
> 但索引也有代价：1）占用磁盘空间；2）会增加写操作的开销，维护索引需要时间；3）对于基数很低的列（比如性别）建索引反而更慢。
>
> 所以我们建索引的原则是：为WHERE条件、JOIN条件、ORDER BY涉及的列建索引，避免给数据量很小或区分度低的列建索引。

### 5. MySQL有哪些索引类型？

#### 5.1 索引分类（按数据结构）

| 索引类型 | 说明 | 使用场景 |
|---------|------|---------|
| **B+Tree索引** | B+树结构，默认类型 | 绝大多数场景 |
| **Hash索引** | 哈希表结构，Memory引擎 | 等值查询 |
| **全文索引** | Full-Text Index | 文本内容搜索 |
| **空间索引** | R-Tree | 地理坐标查询 |

**重点：B+Tree索引**

```
B+Tree结构特点：
- 所有数据存在叶子节点
- 叶子节点链表相连
- 只有叶子节点存完整数据
- 非叶子节点只存指针
```

```
B+Tree vs B-Tree：
┌────────────────┬────────────────┬────────────────┐
│     B-Tree    │   所有节点存数据 │   可以双向遍历 │
├────────────────┼────────────────┼────────────────┤
│   B+Tree      │ 只在叶子节点存 │   单向（范围） │
└────────────────┴────────────────┴────────────────┘
```

#### 5.2 索引分类（按逻辑）

| 索引类型 | 说明 | 示例 |
|---------|------|------|
| **主键索引** | 不允许重复，唯一 | PRIMARY KEY |
| **唯一索引** | 值唯一，允许NULL | UNIQUE |
| **普通索引** | 普通加速 | INDEX |
| **全文索引** | 文本搜索 | FULLTEXT |

#### 5.3 索引分类（按字段个数）

| 索引类型 | 说明 |
|---------|------|
| **单列索引** | 一个字段 |
| **联合索引** | 多个字段 |

#### 5.4 最左匹配原则

**核心概念**：联合索引从最左边开始匹配，顺序很重要！

```sql
-- 创建联合索引
CREATE INDEX idx_a_b_c ON user(a, b, c);

-- 哪些能用到这个索引？
✅ WHERE a = 1
✅ WHERE a = 1 AND b = 2
✅ WHERE a = 1 AND b = 2 AND c = 3

❌ WHERE b = 2    -- 跳过a，从b开始
❌ WHERE c = 3    -- 跳过a、b，从c开始
⚠️ WHERE a = 1 AND c = 3  -- 可以用a，但c用不上
```

**原理**：
```
联合索引的B+Tree结构：
        [a值范围的指针]
           │
    ┌──────┴──────┐
  [a=1]         [a=2]
    │             │
  [b值指针]    [b值指针]
    │             │
 [叶子节点]   [叶子节点]
    │             │
(a,b,c)三元组 (a,b,c)三元组

如果不从a开始，就像找不到书的目录第一章
```

#### 5.5 回答模板

> MySQL主要���以���索引类型：
>
> 1. **按数据结构分**：最常用的是B+Tree索引，所有数据存在叶子节点，叶子节点通过指针相连，支持高效的范围查询。Hash索引是哈希表结构，只有Memory引擎支持，适合等值查询。还有全文索引用于大段文本的搜索。
> 2. **按逻辑分**：主键索引（不允许重复）、唯一索引（值唯一，允许NULL）、普通索引（普通加速）、全文索引（英文/中文文本搜索）。
> 3. **按字段个数分**：单列索引（一列）和联合索引（多列）。
>
> 联合索引有个很重要的原则是「最左匹配」，必须从最左边的列开始匹配。比如索引(a,b,c)，WHERE条件里a必须有值才能使用这个索引，b和c可以用不到，但不能跳过前面的列。这是一个容易被忽视的坑，我之前就见过同事建了联合索引但因为WHERE顺序不对导致没生效。

### 6. InnoDB的索引结构（B+Tree）是怎么工作的？

#### 6.1 B+Tree VS 红黑树

```
为什么不用红黑树（平衡二叉树）？

红黑树：
- 高度：log₂n（100万数据，高度约20）
- 每次IO只能读1个节点
- 100万次IO ≈ 1次

B+Tree：
- 高度：logₘn（m是子节点数，约1200）
- 100万数据，高度约2-3
- 每次IO可以读1个页（16KB）
- 几次IO就能搞定！

结论：B+Tree每个节点可以存更多数据，树更矮，IO次数更少
```

#### 6.2 InnoDB的主键索引结构

```
B+Tree结构示意：
              ┌─────────────┐
              │   根节点   │
              │  (页号指针) │
              └─────┬─────┘
            ┌─────┴─────┐
        ┌───┴───┐   ┌───┴───┐
        │  页1  │   │  页2  │   ← 非叶子节点，存主键+指针
        └───┬───┘   └───┬───┘
          │         │
        ┌──┴──┐ ┌──┴──┐
        │数据1 │ │数据2│ ← 叶子节点，存完整数据+主键
        │     │ │     │
        └─────┘ └─────┘
```

**特点**：
```
1. 主键索引的叶子节点存完整行数据（非叶子节点只存主键+指针）
2. 所有叶子节点通过指针相连，支持范围查询
3. 通过主键查找是O(1)复杂度，最快
```

#### 6.3 InnoDB的二级索引结构

```
二级索引（以name为例）：
              ┌─────────────┐
              │   根节点   │
              │  (name)   │
              └─────┬─────┘
            ┌─────┴─────┐
        ┌───┴───┐   ┌───┴───┐
        │  张三  │   │  李四  │
        └───┬───┘   └───┬───┘
          │         │
        ┌──┴──┐ ┌──┴──┐
        │→id=1│ │→id=2│ ← 叶子节点存主键值，不是完整数据
        └─────┘ └─────┘

查询流程：先找name → 得到主键 → 回表查主键索引 → 得完整数据
```

**回表查询**：二次查询，先在索引树找到主键，再去主键索引树查完整数据。

**如何避免回表？**：用覆盖索引（covering index），查询的列都在索引里。

```sql
-- 刚好索引覆盖，不用回表
CREATE INDEX idx_id_name ON user(id, name);
SELECT name FROM user WHERE id = 1;  -- 直接返回
```

#### 6.4 回答模板

> InnoDB的索引底层是B+Tree数据结构。B+Tree最大的特点是：非叶子节点只存索引+指针，所有数据都存在叶子节点，叶子节点之间通过指针相连。
>
> 对比红黑树：B+Tree的每个非叶子节点可以存多个子节点（一个页约16KB），所以树高很低（一般2-3���）���只需要几次IO就可以找到数据。而红黑树高很多，IO次数多很多。这是InnoDB索引快的关键。
>
> 主键索引的叶子节点存完整行数据，二级索引的叶子节点存主键值。查询时如果是select *，还需要根据主键回表查一次，这叫「回表查询」。为了避免回表，我们可以建立联合索引覆盖需要查询的列，或者只查询索引已有的列。

### 7. 什么是慢查询？如何优化？

#### 7.1 慢查询是什么？

```
MySQL认为「慢」的SQL：
  - 执行时间超过 long_query_time（默认1秒）
  - 会记录到慢查询日志

查看配置：
SHOW VARIABLES LIKE 'slow_query_log%';
SHOW VARIABLES LIKE 'long_query_time';

开启慢查询：
SET GLOBAL slow_query_log = 'ON';
SET GLOBAL long_query_time = 1;
```

#### 7.2 慢查询分析工具：EXPLAIN

```sql
EXPLAIN SELECT * FROM user WHERE id = 1\G

输出字段解释：
  id: 执行的顺序
  select_type: 查询类型（SIMPLE、PRIMARY等）
  table: 查询的表
  type: 连接类型（const、ref、range、ALL等）
  possible_keys: 可用的索引
  key: 实际使用的索引
  key_len: 索引使用长度
  rows: 扫描行数（越少越好）
  Extra: 额外信息（Using filesort、Using temporary等）
```

**type类型排名（从好到差）**：
```
const → eq_ref → ref → range → index → ALL

const：主键或唯一索引等值查询（最好）
eq_ref：多表JOIN，唯一索引
ref：非唯一索引等值查询
range：范围查询（>,
index：索引全扫描
ALL：全表扫描（最差，需要优化）
```

#### 7.3 常见慢查询原因与优化

**原因1：全表扫描**
```sql
-- ❌ 慢：全表扫描
SELECT * FROM user;

-- ✅ 快：走索引
SELECT * FROM user WHERE id = 1;

-- ✅ 即使查询所有列，只要有WHERE条件且有索引，就能用索引
```

**原因2：索引失效**
```sql
-- ❌ 慢：函数操作导致索引失效
SELECT * FROM user WHERE YEAR(create_time) = 2024;

-- ✅ 快：使用函数前先存值，或改写SQL
SELECT * FROM user WHERE create_time BETWEEN '2024-01-01' AND '2024-12-31';

-- ❌ 慢：隐式类型转换（字符串的id被转成数字）
SELECT * FROM user WHERE id = '1';  -- id是INT

-- ✅ 快：类型匹配
SELECT * FROM user WHERE id = 1;
```

**原因3：LIMIT offset过大**
```sql
-- ❌ 慢：先查10000条，再跳过前9990条
SELECT * FROM user LIMIT 10 OFFSET 9990;

-- ✅ 快：利用主键
SELECT * FROM user WHERE id > 9990 LIMIT 10;
-- 或者用覆盖索引
SELECT id FROM user LIMIT 10 OFFSET 9990;
```

**原因4：JOIN过多**
```sql
-- ❌ 问题：JOIN 3张表
SELECT * FROM a JOIN b ON ... JOIN c ON ...

-- ✅ 优化：先过滤缩小结果集，再JOIN
SELECT * FROM a
JOIN (SELECT * FROM b WHERE ...) b ON ...
```

#### 7.4 优化步骤总结

```
1. 开启慢查询日志，找到慢SQL
2. EXPLAIN分析执行计划，观察type、rows、Extra
3. 看有没有走索引（key列）
4. 看扫描行数（rows列）
5. 优化SQL或添加索引
6. 验证效果
```

#### 7.5 回答模板

> 慢查询是指执行时间超过设定阈值的SQL（默认1秒），MySQL会记录到慢查询日志。分析慢查询主要用EXPLAIN命令。
>
> 常见的慢查询优化思路：
> 1. **确保走索引**：看EXPLAIN结果的key列有没有索引，type列最好是ref以上，ALL说明全表扫描。
> 2. **避免索引失效**：不要在WHERE条件用函数、不要类型隐式转换、遵循最左匹配原则。
> 3. **减少回表**：用覆盖索引，查询的列都在索引里。
> 4. **LIMIT优化**：不要offset过大，用主键延迟关联。
>
> 我之前优化过一个慢查询，执行时间3秒。分析发现type是ALL全表扫描，rows显示30万。通过添加合适的联合索引并改写SQL，优化到了100毫秒以内。

### 8. 什么是事务？为什么要用事务？

#### 8.1 事务的概念

**事务**：一组SQL语句，要么全部成功，要么全部失败。

```
转账场景：
  A账户转给B账户100元

  正常：扣A100元 → 加B100元

  ❌ 异常：扣A100元后，系统崩溃
  结果：A少了100，B没收到！

  ✅ 事务：要么都成功，要么都回滚
```

#### 8.2 事务的特性（ACID）

| 特性 | 说明 | 实现方式 |
|-------|------|---------|
| **A**tomic（原子性） | 要么全成功，要么全失败 | Undo Log |
| **C**onsistency（一致性） | 数据始终正确 | 其他三个保证 |
| **I**solation（隔离性） | 并发事务互不影响 | 锁+MVCC |
| **D**urability（持久性） | 提交后不丢失 | Redo Log |

#### 8.3 事务的使用

```sql
-- 开启事务
START TRANSACTION;

-- 或者
BEGIN;

-- 执行SQL
UPDATE account SET balance = balance - 100 WHERE id = 1;
UPDATE account SET balance = balance + 100 WHERE id = 2;

-- 提交
COMMIT;

-- 或者回滚
ROLLBACK;
```

#### 8.4 自动提交

```sql
-- MySQL默认自动提交
SHOW VARIABLES LIKE 'autocommit';

-- 关闭自动提交（手动控制事务）
SET autocommit = 0;

-- 然后手动控制
UPDATE ...;
COMMIT;  -- 或 ROLLBACK;
```

#### 8.5 回答模板

> 事务是一组SQL语句的集合，它们要么全部执行成功，要么全部回滚。典型的例子是转账：A账户扣100元，B账户加100元，这两个操作必须绑定为一个事务，否则扣了钱但对方没收到就完了。
>
> 事务有四个特性（ACID）：原子性（A）保证要么全成功要么全失败；一致性（C）保证数据始终是正确的；隔离性（I）保证并发执行时互不影响；持久性（D）保证提交后数据不丢失。
>
> MySQL默认 autocommit=1，每条SQL自动提交。如果需要事务，可以用 BEGIN...COMMIT 或 START TRANSACTION...COMMIT 来手动控制。

### 9. MySQL有哪些事务隔离级别？

#### 9.1 四个隔离级别

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|---------|------|---------|------|
| READ UNCOMMITTED（读未提交）| ✓ 发生 | ✓ 发生 | ✓ 发生 |
| READ COMMITTED（读已提交） | ✗ 不发生 | ✓ 发生 | ✓ 发生 |
| REPEATABLE READ（可重复读，默认）| ✗ 不发生 | ✗ 不发生 | ✓ 发生 |
| SERIALIZABLE（串行化） | ✗ 不发生 | ✗ 不发生 | ✗ 不发生 |

```
✓ 发生 = 会出现这种问题
✗ 不发生 = 不会有这种问题
```

#### 9.2 问题解释

**脏读**：读到了其他事务未提交的数据
```
事务A：UPDATE user SET money = 1000 WHERE id = 1; (未提交)
事务B：SELECT money FROM user WHERE id = 1; → 读到了1000（脏数据）
事务A：ROLLBACK; → 钱没变，但事务B读到的数据是错的
```

**不可重复读**：同一事务两次读到的数据不一样
```
事务A：SELECT money FROM user WHERE id = 1; → 1000
(其他事务修改并提交了)
事务A：SELECT money FROM user WHERE id = 1; → 2000（和第一次不一样）
```

**幻读**：同一事务两次查到的行数不一样
```
事务A：SELECT * FROM user WHERE id > 10; → 10条
(其他事务插入了新数据)
事务A：SELECT * FROM user WHERE id > 10; → 11条（多了1行）
```

#### 9.3 设置隔离级别

```sql
-- 查看当前隔离级别
SHOW VARIABLES LIKE 'transaction_isolation';

-- 设置隔离级别（会话级）
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;

-- 设置隔离级别（全局级）
SET GLOBAL TRANSACTION ISOLATION LEVEL READ COMMITTED;
```

#### 9.4 回答模板

> MySQL有四个事务隔离级别，处理不同程度的数据一致性问题和并发性能：
>
> 1. **READ UNCOMMITTED（读未提交）**：最低隔离级别，可以看到其他事务未提交的数据，会有脏读、不可重复读、幻读问题。但性能是最好的，一般不用。
> 2. **READ COMMITTED（读已提交）**：MySQL默认（Oracle默认），解决了脏读，但仍有不可重复读和幻读。
> 3. **REPEATABLE READ（可重复读）**：MySQL默认（InnoDB默认），解决了脏读和不可重复读，但仍有幻读问题。实际上InnoDB的MVCC已经解决了大部分幻读问题。
> 4. **SERIALIZABLE（串行化）**：最高隔离级别，解决所有问题，但并发性能最差，相当于加了表级锁。
>
> 一般用默认的REPEATABLE READ就够了，对并发要求特别高的场景可以考虑READ COMMITTED。

### 10. 什么是MVCC？是如何实现的？

#### 10.1 MVCC概念

**MVCC**（Multi-Version Concurrency Control，多版本并发控制）：让每个事务看到的数据「版本」不一样，从而实现并发。

```
不用MVCC：并发时互相等待
  事务A：读（等）
  事务B：写（等）
  事务A：等B写完

用MVCC：各自读自己的版本
  事务A：读版本1
  事务B：写版本2
  并发执行，互不等待
```

#### 10.2 InnoDB的MVCC实现

```
核心三个组件：
1. Undo Log：记录数据的历史版本
2. Read View：事务快照，记录能看到哪些版本
3. 隐藏列：每行有两个隐藏列
   - DB_TRX_ID：最后修改的事务ID
   - DB_ROLL_PTR：指向Undo Log的指针
```

**Read View结构**：
```
Read View = {
    m_ids: [活跃事务ID列表],
    min_trx_id: 最小活跃事务ID,
    max_trx_id: 创建Read View时最大事务ID+1,
    creator_trx_id: 当前事务ID
}
```

**可见性判断**：
```
1. trx_id == creator_trx_id  → 可见（自己改的自己）
2. trx_id < min_trx_id      → 可见（已提交）
3. trx_id > max_trx_id     → 不可见（之后开启的）
4. trx_id in m_ids        → 不可见（未提交的）
不满足上面？查找Undo Log历史版本！
```

#### 10.3 快照读 vs 当前读

**快照读（普通SELECT）**：读取历史版本，不加锁
```sql
SELECT * FROM user WHERE id = 1;
-- 读取的是Read View快照，不是最新数据
```

**当前读（加锁SELECT/UPDATE）**：读取最新数据，加锁
```sql
SELECT * FROM user WHERE id = 1 FOR UPDATE;  -- 写锁
SELECT * FROM user WHERE id = 1 LOCK IN SHARE MODE;  -- 读锁

UPDATE user SET ...;  -- 自动加写锁
```

#### 10.4 回答模板

> MVCC（多版本并发控制）是InnoDB实现高并发的重要机制。它的核心思想是：让每个事务在执行期间看到的是一个「快照」，而不是最新的「实时数据」，从而避免读写冲突。
>
> InnoDB通过三个组件实现MVCC：
> 1. **Undo Log**：记录数据的历史版本，用于回滚和读取历史数据。
> 2. **Read View（读视图）**：记录事务创建时有哪些活跃事务，判断哪些版本可见。
> 3. **隐藏列**：每行数据有两个隐藏列trx_id（事务ID）和roll_ptr（指针），记录修改信息和Undo Log位置。
>
> 判断版本可见性的逻辑是：当前事务ID创建的可以看、小于最小活跃ID的可以看、大于最大ID的不可以看、在活跃列表里的不可以看。
>
> 还有个重要的点是：普通的SELECT是快照读，不加锁；而SELECT...FOR UPDATE 或 UPDATE是当前读，会加锁。

### 11. MySQL的锁机制是什么样的？

#### 11.1 锁的分类

```
按粒度：
  - 行锁：锁定一行
  - 表锁：锁定整张表
  - 页锁：锁定一页（较少）

按模式：
  - 共享锁（S锁）：共享读，不能写
  - 排他锁（X锁）：独占，不能共存

按性质：
  - 意向锁：表级锁，表示有行锁
```

#### 11.2 行锁与表锁

**InnoDB的行锁**：
```sql
-- 加共享锁
SELECT * FROM user WHERE id = 1 LOCK IN SHARE MODE;

-- 加排他锁
SELECT * FROM user WHERE id = 1 FOR UPDATE;
UPDATE user SET ...;  -- 自动加排他锁
```

**MyISAM的表锁**：
```sql
-- MyISAM自动加表锁
LOCK TABLES user READ;
LOCK TABLES user WRITE;
```

#### 11.3 意向锁

```
意向锁是表级锁，表示「我要在表中加行锁」

为什么要意向锁？
  - 判断是否可以加表锁
  - 不用逐行检查是否有行锁
  - 只要检查表级意向锁就行


意向锁类型：
  - IS：有意向加共享锁
  - IX：有意向加排他锁
```

#### 11.4 死锁

```
死锁：两个事务互相等待对方释放锁

场景：
  事务A：锁定行1，等行2
  事务B：锁定行2，等行1
  → 死锁！

解决：
  1. 超时等待（默认50秒）
  2. 死锁检测（默认开启）
  3. 调整SQL顺序
```

```sql
-- 查看死锁信息
SHOW ENGINE INNODB STATUS;
```

#### 11.5 回答模板

> MySQL的锁机制分为行锁和表锁。InnoDB默认是行锁，支持精细的并发控制；MyISAM是表锁，并发性能较差。
>
> 锁的模式有共享锁（S锁）和排他锁（X锁）。意向锁是表级锁，用来快速判断是否可以加表锁，不用逐行检查。
>
> 死锁是两个事务互相等待对方的锁，形成循环等待。InnoDB默认开启死锁检测，会主动回滚其中一个事务来解决死锁。也可以通过调整SQL执行顺序、保持事务简短等方式避免死锁。

### 12. MySQL主从复制的原理是什么？

#### 12.1 主从复制概述

```
主从复制：一台主库（Master），多台从库（Slaves）

目的：
  1. 读写分离：写主库，读从库
  2. 数据备份：从库是备份
  3. 高可用：主库挂了从库上
```

#### 12.2 复制原理

```
┌──────────┐                         ┌──────────┐
│  主库   │  BinLog   │ ───────→ │  从库   │
│  (Master)│          │         │ (Slave) │
└──────────┘                         └──────────┘
  1. 主库写数据到BinLog
  2. Dump线程发送BinLog到从库
  3. 从库IO线程接收，写RelayLog
  4. 从库SQL线程重放RelayLog
```

**三个线程**：
```
主库：
  - Dump线程：给从库发送BinLog

从库：
  - IO线程：接收主库的BinLog，写RelayLog
  - SQL线程：重放RelayLog，执行SQL
```

#### 12.3 三种复制方式

| 方式 | 说明 | 优点 | 缺点 |
|-----|------|------|------|
| **异步复制** | 主库不等从库 | 主库快 | 可能丢数据 |
| **半同步复制** | 主库等至少一个从库返回 | 至少1个从库确认 | 主库稍慢 |
| **全同步复制** | 主库等所有从库 | 不丢数据 | 主库很慢 |

#### 12.4 GTID复制

```
GTID（Global Transaction ID）：全局事务ID

格式：server_uuid:transaction_id
  例：3E11FA47-B3DA:123

优势：
  1. 自动同步，不用指定文件名和位置
  2. 方便搭建主从
  3. 容灾切换更简单
```

#### 12.5 回答模板

> MySQL主从复制是构建高可用架构的基础，原理是主库把所有写操作记录到BinLog，从库通过IO线程拉取并写入RelayLog，再通过SQL线程重放执行。
>
> 复制方式有三种：异步复制（主库不等从库，性能最好但可能丢数据）、半同步复制（等至少一个从库确认，平衡安全和性能）、全同步复制（等所有从库，安全但慢）。
>
> GTID是全局事务ID，可以自动定位复制位置，简化主从搭建，推荐开启。

> 当单表数据量超过一千万条、单库容量达到2-3TB时，就需要考虑分库分表了。
>
> 垂直分库是按业务把表拆分到不同库，如用户库、订单库；垂直分表是把一张表的列拆分到多张表。水平分库/表是把数据按某个字段（如user_id）分散到多个库或表中。
>
> 选择分片键很关键，要求：数据分散均匀、业务经常用来查询、不经常变化。一般选择用户ID或时间。
>
> 生产环境通常用ShardingSphere等中间件来处理分片逻辑。

### 14. 一条SQL语句是如何执行的？

#### 14.1 完整执行流程

```
SQL → 连接器 → 解析器 → 优化器 → 执行器 → 存储引擎

详细步骤：
1. 连接器：建立连��，验证权限
2. 查询缓存：查找是否结果已缓存（MySQL 8.0移除）
3. 解析器：词法分析、语法分析，生成解析树
4. 预处理器：验证表、字段存在，别名解析
5. 优化器：选择索引、制定执行计划
6. 执行器：调用存储引擎，执行SQL
7. 存储引擎：读取/写入数据
8. 返回结果
```

#### 14.2 优化器工作

```
优化器决策：
  - 用哪个索引？
  - 全表扫描还是索引覆盖？
  - JOIN顺序？
  - 是否用临时表？
```

```sql
-- 看优化后的计划
EXPLAIN SELECT * FROM user WHERE id = 1;
```

#### 14.3 执行器工作

```
执行器调用存储引擎的接口：
  - 逐条读取数据（cursor）
  - WHERE条件过滤
  - 返回结果
```

#### 14.4 回答模板

> 一条SQL语句的执行流程是这样的：
> 1. **连接器**：建立连接，验证用户权限。
> 2. **解析器**：进行词法和语法分析，生成解析树。
> 3. **预 processor**：验证表和字段是否存在，进行别名解析。
> 4. **优化器**：选择使用哪个索引、JOIN的顺序、是否使用临时表等，生成执行计划。
> 5. **执行器**：调用存储引擎的接口，按照计划逐条执行。
> 6. **存储引擎**：实际读取或写入数据。
> 7. **返回结果**。
>
> 优化器是最核心的环节，它的决策直接影响SQL性能。我们可以通过EXPLAIN来看优化器的执行计划，根据结果调优SQL。

### 15. MySQL如何保证持久性？

#### 15.1 持久性问题

```
问题：提交后，数据是否一定落到磁盘？

如果只写到内存就断电：
  → 数据丢失！

所以要保证：落盘！
```

#### 15.2 Redo Log

```
Redo Log：重做日志，记录「修改后的数据」

流程：
  1. 事务修改数据 → 先写Redo Log（ prepare）
  2. 写数据到 InnoDB Buffer Pool
  3. 提交事务（commit） → 刷盘
  4. Mark确认

优势：
  - 不是每次都随机写磁盘
  - Redo Log是顺序IO，很快
  - 崩溃后可以从Redo Log恢复
```

```
Redo Log格式：
┌────────────────────┐
│ page_no │ offset │数据  │  ← 修改了哪个页的哪个位置
│ trx_id │ undo   │  new │  ← 具体修改了什么
└────────────────────┘
```

#### 15.3 双1配置

```sql
-- 配置刷盘策略（innodb_flush_log_at_trx_commit）
0：每秒刷盘，不保证持久（性能最好）
1：每次提交刷盘（默认，最安全）
2：提交写到OS缓存，不立即刷盘

生产建议：1
  SET GLOBAL innodb_flush_log_at_trx_commit = 1;
```

#### 15.4 BinLog vs Redo Log

```
Redo Log：InnoDB层的日志，用于崩溃恢复
BinLog：Server层的日志，用于主从复制

区别：
┌──────────────┬──────────────┬──────────────┐
│    层次    │  记录内容  │   使用场景 │
├──────────────┼──────────────┼──────────────┤
│ Redo Log   │ 数据页修改│ 崩溃恢复 │
│ BinLog    │ SQL语句   │ 主从复制 │
└──────────────┴──────────────┴──────────────┘
```

#### 15.5 回答模板

> MySQL的持久性通过Redo Log保证。修改数据时不是直接写磁盘，而是先写Redo Log（顺序IO，很快），然后提交时把Redo Log刷到磁盘。即使崩溃，也可以从Redo Log恢复数据。
>
> 还有一个BinLog，用于主从复制，记录的是SQL语句而不是数据页，这是Server层的日志。两个日志各司其职：Redo Log保证崩溃恢复，BinLog保证主从同步。
>
> 生产环境建议 innodb_flush_log_at_trx_commit 设为1，保证每次提交都刷盘，虽然性能略差但数据不会丢。

### 16. 如何设计MySQL表结构？

#### 16.1 设计原则

```
核心原则：
1. 字段要足够小（占用空间少）
2. 字段要足够简单（避免NULL、复杂类型）
3. 适当的冗余（减少JOIN）
4. 主键要自增（效率高）
```

#### 16.2 数据类型选择原则

| 类型 | 占空间 | 备注 |
|------|--------|------|
| INT | 4字节 |够用就行 |
| BIGINT | 8字节 | 大数值 |
| VARCHAR(n) | n+1字节 | 可变长度 |
| CHAR(n) | n字节 | 定长 |

```
选择建议：
- ID：用BIGINT AUTO_INCREMENT
- 状态：用TINYINT（0-255）
- 布尔：用TINYINT（0/1）
- 名字：用VARCHAR(50)
- 手机：用CHAR(11)或VARCHAR(15)
- 时间：用DATETIME或TIMESTAMP
- 价格：用DECIMAL(10,2)（精准）
```

#### 16.3 字段命名规范

```
命名规则：
- 全部小写
- 用下划线分隔
- 不要用关键字
- 要有意义

✓ user_id / create_time / is_deleted
✗ userId / createtime / status
```

#### 16.4 表结构示例

```sql
CREATE TABLE `user` (
  `id` BIGINT NOT NULL AUTO_INCREMENT COMMENT '主键ID',
  `username` VARCHAR(50) NOT NULL COMMENT '用户名',
  `mobile` CHAR(11) NOT NULL COMMENT '手机号',
  `email` VARCHAR(100) DEFAULT NULL COMMENT '邮箱',
  `status` TINYINT NOT NULL DEFAULT '1' COMMENT '状态：1正常',
  `create_time` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `update_time` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_username` (`username`),
  KEY `idx_mobile` (`mobile`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户表';
```

#### 16.5 回答模板

> MySQL表设计有一些原则：
> 1. 主键用自增的BIGINT，不要用UUID（占空间且无序）。
> 2. 字段类型要合适，能用TINYINT就不用INT，节省空间。对于可变长度用VARCHAR，定长用CHAR。
> 3. 要设置默认值为NULL，少用NOT NULL（除非必须）。时间字段用DATETIME或TIMESTAMP。
> 4. 每一列都要加COMMENT，方便维护。
> 5. 必须加索引：主键、唯一键、常用来WHERE的字段。
>
> 我通常会预留一些冗余字段，避免后续JOIN太多表，也方便扩展。

### 17. 如何选择合适的存储引擎？

#### 17.1 选择决策树

```
是否需要事务？
├── 是 → InnoDB
└── 否
    ├── 并发高 → InnoDB
    └── 只读/静态 → MyISAM
```

#### 17.2 InnoDB使用场景

```
✓ 需要事务支持
✓ 并发写入多
✓ 需要行级锁
✓ 需要崩溃恢复
✓ 数据重要
```

#### 17.3 MyISAM使用场景

```
✓ 纯读表（报表、日志）
✓ 不需要事务
✓ 不需要崩溃恢复
✓ 旧系统兼容
✓ 全文检索（老的FULLTEXT）
```

#### 17.4 回答模板

> 开发中99%的情况下用InnoDB就够了，它是默认引擎，支持事务和行级锁，崩溃后可以自动恢复。
>
> 唯一可能用MyISAM的场景是那些纯粹用来读的静态表，比如报表数据、日志归档，这类表不需要事务，也不怎么更新，用MyISAM查询会稍快一点，但现在已经很少用了。

### 19. 数据库连接池如何配置？

#### 19.1 为什么用连接池

```
不用连接池：
  每次请求 → 建立连接 → 执行 → 关闭连接
  → 耗时300ms，连接资源浪费

用连接池：
  预先建立N个连接
  请求 → 拿连接 → 执行 → 还连接
  → 耗时10ms，复用连接
```

#### 19.2 主要参数

```
HikariCP配置示例：
spring.datasource.hikari.maximum-pool-size=20   最大连接数
spring.datasource.hikari.minimum-idle=5          最小空闲
spring.datasource.hikari.connection-timeout=30000  超时30秒
spring.datasource.hikari.idle-timeout=600000        空闲10分钟
spring.datasource.hikari.max-lifetime=1800000         最大生存30分钟
```

#### 19.3 参数计算

```
公式：
  建议最大连接数 = CPU核心数 × 2 + 磁盘数
  例如：4核CPU + 1块SSD = 9个连接

经验值：
  - IO密集型：更大（等待多）
  - CPU密集型：更小（计算多）
```

#### 19.4 回答模板

> 连接池是必须的，它可以复用数据库连接，避免每次请求都建立新连接的开销。主要参数有：
> 1. **maximum-pool-size**：最大连接数，一般CPU核心数×2+磁盘数。
> 2. **minimum-idle**：最小空闲连接，保持一些连接预热。
> 3. **connection-timeout**：获取连接超时，超过则报错。
> 4. **idle-timeout**：空闲连接多久回收。
> 5. **max-lifetime**：连接最大生命周期，到期强制回收。
>
> 我们公司用HikariCP，最大连接数设为20，平时连接池使用率在50%~80%之间，比较健康。

### 20. 分页查询如何优化？

#### 20.1 基础分页

```sql
-- 基础分页
SELECT * FROM user LIMIT 10 OFFSET 0;

-- 带WHERE的分页
SELECT * FROM user WHERE status = 1 ORDER BY id LIMIT 10 OFFSET 0;
```

#### 20.2 OFFSET过大问题

```sql
-- ❌ 慢：OFFSET 100万，先扫100万行
SELECT * FROM user LIMIT 10 OFFSET 1000000;

-- ✅ 快：基于主键
SELECT * FROM user WHERE id > 1000000 LIMIT 10;

-- ✅ 快：先查ID再JOIN
SELECT u.* FROM user u
INNER JOIN (SELECT id FROM user LIMIT 10 OFFSET 1000000) t ON u.id = t.id;
```

#### 20.3 游标分页

```python
# 服务端游标分页
last_id = 0
while True:
    users = db.query("SELECT * FROM user WHERE id > ? ORDER BY id LIMIT 20", last_id)
    if not users:
        break
    last_id = users[-1]['id']
    process(users)
```

#### 20.4 回答模板

> 分页查询优化有几个常用技巧：
> 1. **避免大OFFSET**：不要用LIMIT 10 OFFSET 100万这种，可以记录上一页Last ID，用WHERE id > Last ID代替。
> 2. **游标分页**：用ID作为游标，每次只往后翻一页，适合无限滚动场景。
> 3. **覆盖索引分页**：先只查ID，再用INNER JOIN获取完整数据。
>
> 我们项目的分页都是用游标分页做的，用户体验稳定，也不存在性能问题。
