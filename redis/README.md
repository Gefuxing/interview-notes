## 第零章 入门铺垫 —— 理解Redis的基础概念

### 为什么要先学这个？

在学习具体问题之前，我们需要先建立一个整体认知。这就像盖房子要先打地基，地基稳了，后续的知识才能理解的更好。

#### 0.1 什么是Redis？

**一句话定义**：Redis是一个「**存放在内存中的数据库**」。

我们来拆解这句话：

1. **数据库**：意味着它可以存储数据，像MySQL、Oracle一样
2. **内存中**：数据是存放在RAM（随机存取存储器）里，而不是硬盘

**这很奇怪**，不是吗？我们平常接触最多的MySQL是把数据存在硬盘（磁盘）上的。Redis为什么要存在内存里？

**答案：因为内存比硬盘快太多了！**

让我们做个简单的数学题：
- 机械硬盘读取一个数据大概需要 **10毫秒**
- 固态硬盘大概是 **0.1毫秒**
- 内存读取只需要 **0.001毫秒**（甚至更快）

也就是说，内存比机械硬盘快 **10000倍**！比固态硬盘快 **100倍**！

这就解释了为什么Redis能够「每秒处理十几万次请求」，而传统数据库可能只能处理几千次。

但是这里有个问题：**内存是会丢数据的**。想象一下如果你电脑停电了，内存里的数据就没了。但是硬盘不会。所以Redis后来又加入了一些机制来 保证数据不丢失，这个后面会详细讲。

#### 0.2 Redis可以做什么？

虽然Redis很快，但它不能替代所有数据库。它最适合的场景是：

**1. 缓存（Cache）**
```
传统方式：用户请求 → 查数据库 → 返回数据
Redis方式：用户请求 → 查Redis → 直接返回（如果缓存里有的话）
          ↓ （如果没有）
          查数据库 → 写入Redis → 返回数据
```

**2. 分布式锁**
想象一下，你有一个购票系统，有很多台服务器同时服务。如果不加锁，可能会卖出同一张票！Redis可以帮助解决这个问题。

**3. 实时排行榜**
游戏里谁的分数最高？谁的装备最好？Sorted Set可以轻松实现。

**4. 消息队列**
可以用于异步处理任务，比如下单后发短信、发邮件等。

**5. 计数器和限流**
网站的访问量统计、接口限流等。

#### 0.3 为什么Redis那么快？

这个问题在面试中经常被问到，我们来详细分析：

**核心原因1：数据在内存里**

这个刚才说过了。最关键的原因是数据就在RAM里，不需要去读写硬盘。

**核心原因2：单线程 + IO多路复用**

这里有两个概念需要解释：

① **单线程**：很多人听到单线程就会想「那不是很慢吗」。其实不然。单线程避免了「线程切换」的开销。

想象一下你在餐厅吃饭：
- 多线程：如果有很多服务员，服务员A正在给你点菜，服务员B突然说要服务另一桌，于是放下你的菜单，去服务另一桌——这就是「线程切换」
- 单线程：只有一个服务员，不会换来换去，专心服务你一个人

Redis就是这个「单一服务员」，它的任务就是处理你的请求，不会换来换去，所以效率很高。

② **IO多路复用**：这是Unix/Linux的一个高级特性。简单说就是一个进程可以同时处理很多个网络连接。

Epoll是Linux的一个内核功能，它让Redis可以用一个线程同時監視成千上万个连接，哪个有数据来了就去处理哪个。这就是为什么Redis能「高并发」。

**核心原因3：高效的数据结构**

Redis为每种数据类型都设计了专门的「底层实现」。就像不同的货物要用不同的货车来装：
- 短字符串 → 用小箱子（C中的SDS）
- 大量整数 → 用特殊的整数数组（Int Set）
- 有序列表 → 用「跳表」（Skip List）

这些后面会详细讲。你只需要知道，每种类型都有针对性的优化。

**核心原因4：预分配 + 懒删除**

Redis会预先分配一些内存空间，就像批发商一次性进很多货，放在仓库里备用。当要删除数据时，不是立刻回收空间，而是标记为「可以再用」，下次要用就不用再申请新空间了。

## 第一章 基础概念篇（高频 ★★★★★）

### 1. 什么是Redis？为什么要用Redis？

这个问题看似简单，但面试官想听的不仅是定义，而是你对Redis的整体认知。

#### 1.1 标准的回答模板

> Redis（全称：Remote Dictionary Server，远程字典服务器）是一个**开源的、基于内存的、K-V键值对存储系统**。它可以用作**数据库、缓存和消息队列**。

我来逐个解释这些术语：

**开源（Open Source）**：源代码是公开的，你可以免费使用，也可以修改。现在由VMware旗下的Redis Labs维护。

**基于内存（In-Memory）**：数据存储在RAM中，这是它快的根本原因。

**K-V键值对（Key-Value）**：这是一种最简单的数据存储方式。
- Key（键）：就像是变量的名字，比如 `user:1001`
- Value（值）：就是对应的数据，比如 `{name: "张三", age: 25}`

这就像Python里的字典：
```python
user_info = {
    "name": "张三",
    "age": 25,
    "city": "北京"
}
```

**数据库、缓存、消息队列**：
- 作为「数据库」：可以直接存储和查询数据
- 作为「缓存」：把热数据放在里面加速访问
- 作为「消息队列」：可以异步处理任务

#### 1.2 为什么要用Redis？（背也要背下来）

面试中经常会问「为什么用Redis」「为什么不用XXX」，你需要从以下几个角度回答：

**角度1：高性能**

```
速度对比（理论值，实际会有差异）：
┌─────────────────┬────────────────────┐
│ MySQL查询       │ 约 1,000-10,000次/秒 │
│ Redis查询      │ 约 100,000+ 次/秒    │
└─────────────────┴────────────────────┘
差距：10-100倍！
```

原因就是前面说的：内存 vs 硬盘。

**角度2：丰富的数据结构**

Redis不仅仅支持字符串，还支持：
- 哈希表（Hash）
- 列表（List）
- 集合（Set）
- 有序集合（Sorted Set）
- 位图（Bitmap）
-HyperLogLog
- 地理位置（GEO）

这些数据结构在某些场景下非常有用。比如排行榜，用Sorted Set可以实现高效排名。

**角度3：单线程 + IO多路复用**

这个前面解释过了。高并发不再是问题。

**角度4：丰富的特性**

- 持久化：可以把内存数据保存到硬盘
- 事务：可以批量执行命令
- 发布/订阅：可以实现消息推送
- Lua脚本：可以自定义复杂逻辑
- Pipeline：可以批量执行命令减少网络开销

#### 1.3 回答示例

面试时你可能要这样回答：

> Redis是一个开源的、基于内存的键值对存储系统，由Salvatore Sanfilippo开发。它之所以被广泛使用，主要有以下几点原因：
>
> 1. **性能极高**：因为数据存放在内存中，读取速度可以达到每秒十几万次，比传统的数据库快很多。这点在需要快速响应的场景下特别重要。
> 2. **���持��种数据结构**：String、Hash、List、Set、Sorted Set等都支持，而且每种数据类型都做了专门的优化，可以根据业务需求选择最合适的数据类型。
> 3. **单线程 + IO多路复用**：虽然看起来是单线程，但实际上可以通过IO多路复用技术同时处理海量的并发连接，效率非常高。
> 4. **丰富的功能**：支持持久化、事务、Lua脚本、发布订阅、Pipeline等特性，可以满足各种复杂的业务需求。
>
> 在实际项目中，我们通常会把Redis用作缓存层，把热点数据放进去，加速访问。比如电商商品的详细信息、用户的Session、接口的限流等。

### 2. Redis为什么这么快？

这是一个经典的八股文问题，但也是区分你有没有真正理解Redis的关键。

#### 2.1 原因一：纯内存操作

**核心观点**：数据在内存里，这是所有快的前提。

我们来深入理解：「内存」和「硬盘」到底有什么区别？

```
📦 这里用一个比喻：
- 内存（RAM）就像是你的书桌：拿东西超级快，但是只能放很少的东西，而且断电就没了
- 硬盘（Disk）就像是图书馆的仓库：可以放很多很多的东西，但是要找需要时间

Redis就是那个「永远把常用的书放在书桌上」的系统。
```

这里还有一个隐藏的考点：**为什么内存比硬盘快？**

硬件原理：
- 硬盘是机械的，要转动磁头去找数据（就像DVD机读盘）
- 内存是电子的，直接通过电路访问（就像直接从大脑回忆）

**结论**：所以只要是需要频繁读取的数据，放在Redis里准没错！

#### 2.2 原因二：单线程模型

**这个点很多人理解错了！**

很多人想：「单线程？那岂不是会很慢？」

**错了！** 这里的「单线程」不是我们平常意义上的「单」。

**解释1：不等于慢**

```
CPU有两大指标：
1. 算力：每秒能执行多少指令
2. IO：每秒能读写多少数据

Redis的性能瓶颈通常是「IO」，不是「算力」。
如果是CPU密集型任务（比如加密），单线程确实会慢。
但Redis主要是「IO密集型」，单线程完全够用！
```

**解释2：避免了锁的开销**

```
多线程的痛：
线程A正在读写数据
线程B也要读写同一份数据
→ 需要加锁
→ 锁的实现很复杂
→ 会降低性能

Redis说：我就一个线程，别争了！
```

**解释3：没有线程切换开销**

```
CPU在各个线程之间切换是有成本的：
1. 保存当前线程的执行状态
2. 加载另一个线程的执行状态
3. 清空缓存（不同线程使用的CPU缓存不一样）

单线程：完美避开这些问题！
```

**补充：Redis 4.0之后也有多线程了！**

准确地说：
- 命令执行层面：单线程
- 后台任务层面：有多线程（lazy delete、 unloaded keys等）

#### 2.3 原因三：IO多路复用

这是让Redis能用单线程处理高并发的关键技术！

**解释什么是IO多路复用：**

想象你在餐厅当服务员：
- **普通方式**：
  - 顾客A点菜 → 你去服务 → 等着做菜 → 上菜
  - 顾客B点菜 → 你去服务 → ...
  - 同时只能服务一个顾客！

- **IO多路复用**：
  - 顾客们都在等着（有顾客来时餐厅会通知你）
  - 你可以同时「监视」所有顾客
  - 谁需要服务就去服务谁
  - 服务完马上回来继续监视

在Linux系统中，这个技术叫做 **Epoll**。Redis用它来实现「一个线程处理海量并发连接」。

**代码级别的理解：**

```c
// 没有IO多路复用的情况
while(true) {
    read(socket1, ...);
    read(socket2, ...);
    read(socket3, ...);  // 阻塞！
}

// 有IO多路复用
while(true) {
    // 这是一个高效的系统调用，返回哪些socket有数据
    events = epoll_wait(epfd, ...);
    for (每个有数据的socket) {
        处理请求;
    }
}
```

#### 2.4 原因四：高效的数据结构

这个会在后面「数据类型」章节详细讲。这里先预告一下：

```
String（字符串）
↓ 底层实现：SDS（简单动态字符串）
→ 比C语言的字符串高效在哪里？O(1)获取长度！

Hash（哈希表）
↓ 底层实现：字典 + 渐进式rehash
→ 完美解决hash冲突问题！

Sorted Set（有序集合）
↓ 底层实现：Skip List（跳表）+ 字典
→ 查找是O(1)，排序是O(logN)！
```

#### 2.5 原因五：预分配 + 懒删除

这两个优化让Redis减少了内存分配的开销。

**预分配（Pre-allocation）**

```c
// 比如你要存一个字符串"hello"
// 普通方式：用多大的空间就申请多大的
// Redis方式：先多申请一点，防止不够用
// 就像买衣服「买大一点」，长高了还能穿
```

**懒删除（Lazy Free）**

```
普通方式：删除数据 → 立刻回收内存 → 有成本
Redis方式：标记为「可删除」→ 什么时候有空什么时候删
        → 顺带清空碎片
```

#### 2.6 回答示范

> Redis之所以这么快，主要有以下几个原因：
>
> 1. **纯内存操作**：所有的数据都存储在内存中，访问速度比磁盘快几个数量级。这是性能高的根本。
>
> 2. **单线程模型**：虽然是单线程，但恰好避开了线程切换和锁竞争的开销。而且Redis是IO密集型而非CPU密集型，单线程完全够用。
>
> 3. **IO多路复用**：使用了Linux的epoll技术，一个单线程可以同时监视海量连接，谁有数据就处理谁，实现了高并发。
>
> 4. **高效的数据结构**：每种数据类型都用了专门设计的底层实现。比如String用SDS，Hash用字典+渐进式rehash，Sorted Set用跳表+字典。都是经过优化的。
>
> 5. **内存优化**：采用了预分配和懒删除策略，减少了内存分配和回收的开销。

### 3. Redis有哪些数据结构？

这是必问题！必须倒背如流！

#### 3.1 先理解「数据结构」是什么？

新手可能会有疑问：「什么String、Hash、List的，不就是数据类型吗？为什么叫数据结构？」

**数据类型 vs 数据结构**：
- **数据类型**：数据长什么样。比如「字符串」就是一种数据类型
- **数据结构**：数据怎么存、怎么组织。比如同样是「字符串」，Redis用的是SDS

在这个语境下，两者差别不大，面试时不用纠结。

#### 3.2 八大数据类型详解

##### 类型1：String（字符串）

**怎么用？**
```
SET name "张三"      → 设置值
GET name            → 获取值
INCR counter       → 自增1
DECRBY counter 5   → 减5
```

**底层实现**：SDS（Simple Dynamic String，简单动态字符串）

**特点**：
- 可以存储任何内容：字符串、数字、JSON、序列化对象
- 最多512MB（二进制安全）

**应用场景**：
- 缓存页面：`SET page:home "<html>..."`
- 计数器：`INCR views:article:123`
- 分布式锁：`SET lock:order "uuid" NX EX 30`

---

##### 类型2：Hash（哈希表）

**怎么用？**
```
HSET user:1001 name "张三" age 25
HGET user:1001 name
HGETALL user:1001
```

**数据结构**：ZipList（压缩列表）或Dict（字典）

**适用场景**：
- 存对象：`user:1001` → `{name: "张三", age: 25, city: "北京"}`
- 购物车：`cart:user:1001` → `{item:123: 2, item:456: 1}`

**为什么不用String存对象？**
```
用String：
SET user:1001 '{"name":"张三","age":25}'
→ 每次修改都要序列化和反序列化

用Hash：
HSET user:1001 name "张三"
HSET user:1001 age 25
→ 可以单独修改某个字段
```

---

##### 类型3：List（列表）

**怎么用？**
```
LPUSH mylist "a"       → 左边插入
RPUSH mylist "b"       → 右边插入
LPOP mylist            → 左边弹出
RPOP mylist            → 右边弹出
LRANGE mylist 0 -1     → 遍历
```

**数据结构**：QuickList（快速列表）= ZipList + 双向链表

**特点**：
- 有序
- 可以重复
- 支持两端操作

**应用场景**：
- 消息队列：`LPUSH queue:task task_id`
- 最新列表：`LPUSH latest:articles article_id`
- 关注列表timeline

---

##### 类型4：Set（集合）

**怎么用？**
```
SADD tags:article:123 "redis" "mysql" "database"
SMEMBERS tags:article:123
SISMEMBER tags:article:123 "redis"
```

**数据结构**：IntSet（整数集合）或Dict

**特点**：
- 无序
- 去重
- 支持交集、并集、差集

**应用场景**：
- 标签：`SADD tags:123 tag1 tag2`
- 共同好友：`SINTER friends:1001 friends:1002`
- 抽奖：`SRANDMEMBER prize:pool 10`

---

##### 类型5：Sorted Set（有序集合）

**怎么用？**
```
ZADD leaderboard 100 "player1" 200 "player2" 150 "player3"
ZRANGE leaderboard 0 -1 WITHSCORES  // 从低到高
ZREVRANGE leaderboard 0 9 WITHSCORES // 前10名
ZINCRBY leaderboard 50 "player1"     // 加分
```

**数据结构**：SkipList（跳表） + Dict

**特点**：
- 有序（按照score排序）
- 去重
- 支持范围查询

**应用场景**：
- 排行榜
- 延迟队列
- 按距离排序

**为什么比List更适合做排行榜？**

```
List：要查第10名，需要遍历10次 → O(N)
Sorted Set：直接跳过 → O(logN)
```

---

##### 类型6：BitMap（位图）

**怎么用？**
```
SETBIT sign:1001:2024 0 1    // 第1天签到
GETBIT sign:1001:2024 0       // 查看第1天是否签到
BITCOUNT sign:1001:2024      // 统计签到天数
BITOP AND result key1 key2   // 多个用户求交集
```

**底层实现**：就是字符串，但是对「位」进行操作

**特点**：
- 节省空间：一个比特存是/否
- 适合做状态标记

**应用场景**：
- 用户签到：`SETBIT sign:user:2024-01 day 1`
- 活跃用户统计
- 布隆过滤器（底层用到）

**空间占用示例**：
```
一年365天，用String：365字节
用BitMap：365位 ≈ 46字节
节省：87%！
```

---

##### 类型7：HyperLogLog

**怎么用？**
```
PFADD uv:2024-01-01 user123 user456 user789
PFCOUNT uv:2024-01-01
PFADD uv:2024-01-02 user234 user456
PFMERGE uv:2024-01 uv:2024-01-01 uv:2024-01-02
```

**作用**：基数估算（就是统计「有多少个不同的元素」）

**特点**：
- 不存储具体元素，只存「估计值」
- 非常节省内存：12KB可以存2^64个
- 有误差，但是很小（±0.81%）

**应用场景**：
- 统计每日UV（独立访客）
- 统计活跃用户数
- 统计搜索词不重复数

---

##### 类型8：GEO（地理位置）

**怎么用？**
```
GEOADD location 116.4074 39.9042 "北京"
GEOADD location 121.4737 31.2304 "上海"
GEODIST location "北京" "上海" KM  // 两地距离
GEORADIUS location 116.4074 39.9042 1000 KM WITHDIST  // 附近1000km的人
```

**底层实现**：geohash编码 + Sorted Set

**特点**：
- 存储经纬度
- 计算两点距离
- 查找附近的人

## 第二章 深入理解底层实现

这一章是区分「只会用」和「真的懂」的关键！

### 4. String类型的底层实现？

#### 4.1 为什么要有SDS？

我们知道，C语言已经有字符串了，为什么Redis还要自己实现一个？

**C字符串的问题**：
```c
char str[] = "hello";  // 长度为5，加上结尾的\0是6个字符
```

问题1：**获取长度是O(N)**
```c
strlen(str);  // 需要从头数到尾，才能知道长度
            // 每用一次就要数一遍！
```

问题2：**二进制不安全**
```c
// 如果字符串里包含\0，C语言会认为是结尾
char data[] = "hello\x00world";
strlen(data);  // 返回5，因为遇到\0就停了
              // 但实际上字符串是"hello\0world"！
```

问题3：**拼接要重新分配内存**
```c
strcat(dest, src);  // 可能需要扩容
// 中间有好几步，开销很大
```

#### 4.2 SDS是如何解决的？

```c
struct sdshdr {
    int len;    // 🔑 记录已使用的长度
    int free;  // 🔑 记录剩余空间
    char buf[];// 实际存放数据
};
```

**解决方案1：O(1)获取长度**
```
直接读 len 字段就行了！
strlen → return sdshdr.len
```

**解决方案2：二进制安全**
```
靠 len 字段判断末尾，而不是 \0
所以可以存任何二进制数据
```

**解决方案3：空间预分配**
```
当空间不够时，一次性多分配一些
避免每次拼接都要扩容
```

**解决方案4：惰性释放**
```
删除数据时，不是真的删除空间
而是把 free 加上去，随时可以复用
```

#### 4.3 图解SDS vs C字符串

```
C字符串：
┌───┬───┬───┬───┬───┬────┐
│ h │ e │ l │ l │ o │ \0 │
└───┴───┴───┴───┴───┴────┘
 0   1   2   3   4   5   6
（需要遍历才能知道长度）

SDS：
┌─────┬─────┬───────────────────┐
│ len │free│ h │ e │ l │ l │ o │
└─────┴─────┴───────────────────┘
    5    0    0   1   2   3   4
（直接读 len = 5，马上知道长度）
```

#### 4.4 回答模板

> String类型使用的是SDS（Simple Dynamic String，简单动态字符串）结构。这个是Redis自行设计的一种���符串实现，相比C语言的原声字符串有几个优势：
>
> 1. **O(1)复杂度获取长度**：SDS有一个len字段，直接读取就行，不需要遍历。C字符串需要O(N)。
> 2. **二进制安全**：C字符串用\0判断结尾，所以不能包含\0。SDS用len字段判断，可以存储任何二进制数据。
> 3. **空间预分配**：当字符串增长时，SDS会预分配更多空间，减少内存分配次数。
> 4. **惰性释放**：删除数据时不立即回收空间，而是增加free，方便下次复用。
>
> 这些设计让Redis的字符串操作更高效，也是Redis整体高性能的原因之一。

### 5. Hash表是如何实现的？如何解决哈希冲突？

这是数据结构的核心！面试必问！

#### 5.1 基本概念

**什么是Hash表？**
```
Key → Hash函数 → Hash值 → 存放到对应位置

比如：
"user:1001" → Hash函数 → 位置3 → 存到数组的第3个位置
```

**优点**：查找快，平均O(1)
**缺点**：可能有冲突

#### 5.2 什么是哈希冲突？

**冲突**的意思是：两个不同的Key，经过Hash函数后，得到了相同的位置。

```
Key1 = "apple"  → Hash → 位置3
Key2 = "banana" → Hash → 位置3
→ 这就是冲突！
```

#### 5.3 Redis的解决方案：链地址法

```
数组：
┌───┬───┬───┬───┬───┬───┐
│ 0 │ 1 │ 2 │ 3 │ 4 │ 5 │
└───┴───┴───┴───┴───┴───┘
              ↓
            ┌───────┐
            │ apple │ → null
            └───────┘
冲突时（新来的banana）：
              ↓
            ┌───────┐      ┌───────┐
            │ apple │ ──→  │banana │ → null
            └───────┘      └───────┘
（像一个链表，挂在一起）
```

这种方式叫做「链地址法」或「拉链法」。

#### 5.4 渐进式rehash

**问题**：如果Hash表要扩容怎么办？

**普通做法**：一次性迁移
- 创建一个更大的数组
- 把所有数据都搬过去
- 期间不能读写，会阻塞

**Redis的做法**：渐进式rehash
```
1. 创建新数组（更大）
2. 把迁移操作分散到每次读写中
   - 每次读写，顺带迁移一个桶
   - 分多次完成，不阻塞
3. 迁移期间：两个数组都用
   - 新数据放新数组
   - 查询两边都查
4. 完成后：新数组变主数组，旧数组释放
```

**为什么这样设计？** 假设有1000万数据，一次性迁移会阻塞几秒钟。用渐进式rehash，每次只需要迁移一点点，完全无感！

#### 5.5 图解渐进式rehash

```
阶段1：ht[0] 有数据，ht[1] 空
┌─────────────────────────────────────┐
│ ht[0]: [桶0, 桶1, ..., 桶N]           │
│ ht[1]: []                           │
└─────────────────────────────────────┘

阶段2：开始rehash
┌─────────────────────────────────────┐
│ ht[0]: [部分数据] → 逐步转移到 →     │
│ ht[1]: [部分数据] ← 每操作迁一个桶   │
└─────────────────────────────────────┘

阶段3：rehash完成
┌─────────────────────────────────────┐
│ ht[0]: []  （释放）                  │
│ ht[1]: [完整数据]                    │
└─────────────────────────────────────┘
```

#### 5.6 回答模板

> Redis的Hash表使用**链地址法**来解决哈希冲突。具体的做法是：每个数组位置（桶）下面挂一个链表，如果有冲突，就接到链表后面。
>
> 为了解决扩容时的阻塞问题，Redis采用了**渐进式rehash**：
> 1. 创建两个Hash表（ht[0]和ht[1]），ht[1]比ht[0]大一倍
> 2. 迁移操作分散到每一次读写中，每次顺带迁移一个桶
> 3. 迁移期间，新数据写入ht[1]，查询时两边都查
> 4. 迁移完成后，ht[1]变成新的ht[0]，旧表释放
>
> 这种设计保证了即使Hash表在扩容，也不会阻塞服务，体验非常好。

### 6. List、Set、Sorted Set的底层实现？

这三个类型要分开讲，因为实现各不相同。

#### 6.1 List的实现：QuickList

**演变过程**：
1. 早期：只用LinkedList（双向链表）
   - 优点：插入删除O(1)
   - 缺点：每个节点都有指针，空间开销大

2. 后来：只用ZipList（压缩列表）
   - 优点：紧凑，省空间
   - 缺点：中间插入/删除O(N)

3. 现在：QuickList = 两者结合！
   ```
   [ZipList] ↔ [ZipList] ↔ [ZipList]

   每个ZipList最多存一定数量的元素（默认64个）
   元素多的时候会自动开新的
   ```

**为什么这样做？**
```
zipList 太长 → 中间操作慢
linkedList 太散 → 内存碎片多

quickList：平衡两者！
- 没变太长 → 是一个ZipList，操作快
- 变长了 → 自动分裂成多个ZipList，灵活
```

#### 6.2 Set的实现：IntSet + Dict

**当所有元素都是整数时**：用IntSet
```
┌─────────────────────────────┐
│ encoding │ length │ elem[]  │  // 像一个数组，紧密排列
└─────────────────────────────┘

优点：省空间！查找快！

⚠️ 只要有一个不是整数，立刻转换为Dict
```

**其他情况**：用Dict
```
和Hash一样的实现：数组 + 链表（或者升级为Dict+哈希表）
```

#### 6.3 Sorted Set的实现：SkipList + Dict

这是最复杂、也是最重要的数据结构！必问！

**先理解SkipList（跳表）**：一种「链表」+「索引」的结构，让查找像二分查找一样快！

```
普通链表：
a → b → c → d → e → f → g
要找到f，需要遍历6次

跳表（加了索引）：
一级索引：a ────────── e ───────
二级索引：a ───── c ───── e ───── g
         ↓               ↓      ↓
原始链表：a → b → c → d → e → f → g

要找到f：
1. 二级索引看到e，发现e<目标，继续
2. 继续找e，跳到位置6
3. 找到了！

这就是为什么Sorted Set查找是O(logN)级别的原因！
```

**Dict的作用**：O(1)找到某个元素的分数

```
Sorted Set = SkipList（有序）+ Dict（快速查分）

用户查"player1"的分数：
→ Dict直接找到位置 → SkipList读分数
时间复杂度：O(logN)查排名 + O(1)查分数 = 都快！
```

#### 6.4 回答模板

> 这三种数据类型的底层实现各不相同：
>
> **List（列表）**：现代版本使用的是QuickList，也就是「压缩列表+双向链表」的组合。每个QuickListNode包含一个ZipList，多个节点串在一起。这样既保持了较好的内存利用率，在头部或尾部操作时也非常高效。
>
> **Set（集合）**：有两种实现。一种是IntSet（整数集合），当所有元素都是整数时使用，非常节省空间。另一种是Dict，当元素不是纯整数时使用，和Hash表的实现类似。
>
> **Sorted Set（有序集合）**：使用的是SkipList（跳表）和Dict的组合。SkipList保证元素是有序的，查找是O(logN)；Dict保证可以通过Key直接找到位置，查询分数是O(1)��这也是Redis的有序集合比其他实现更快的原因。

## 第三章 持久化机制 —— 数据怎么保存？（中高频 ★★★★）

### 7. Redis有哪些持久化方式？

持久化是Redis的核心功能！数据存在内存里，如果不持久化，断电就没了！

#### 7.1 两种持久化方式的区别

**RDB（Redis Database）**：定时生成「快照」
```
某一时刻的所有数据 → 生成一个文件（RDB文件）
恢复时：直接读取这个文件
```

**AOF（Append Only File）**：记录「写操作命令」
```
每次执行写操作 → 追加一条记录到文件
恢复时：重新执行所有命令
```

#### 7.2 RDB详解

**触发方式**：
```
1. 手动触发：
   - SAVE：同步，会阻塞！
   - BGSAVE：异步（fork子进程）

2. 自动触发（根据配置）：
   - 1分钟内改了1万次
   - 5分钟内改了10次
   - 6小时内改了100次
```

**流程图**：
```
主进程
  ↓ fork bgrewriteaof
子进程（BGSAVE)
  ↓ 遍历内存
dump.rdb（完整数据）
  ↓ 写入
磁盘 → 保存成功
```

**优点**：
- 文件小（压缩过）
- 恢复快（一次性加载）

**缺点**：
- 可能丢失数据（最后一次SAVE到现在的）
- fork耗时（大数据很慢）

#### 7.3 AOF详解

**三种同步策略**：
```
appendfsync always    ← 每个命令都同步（最安全，但最慢）
appendfsync everysec ← 每秒同步（推荐，默认）
appendfsync no       ← 看操作系统（最快，但可能丢数据）
```

**流程图**：
```
写命令 → 追加到AOF缓冲区 → 同步到磁盘
```

**为了避免文件太大**，AOF会「重写」：
```
bgrewriteaof：fork子进程，压缩AOF文件
- 去掉无效命令
- 合并重复命令
例：INCR num 10次 → SET num 10
```

#### 7.4 混合模式

Redis 4.0之后推出了「混合持久化」：
```
AOF文件前半部分是RDB格式
后半部分是AOF格式

┌────────────────────────────┐
│    RDB格式（完整数据）       │
│    AOF格式（增量命令）       │
└────────────────────────────┘
```

**为什么好？**：
- RDB部分恢复快
- AOF部分不丢失数据

#### 7.5 回答模板

> Redis有两种持久化方式：RDB和AOF。
>
> **RDB**是在某个时刻把所有数据生成一个快照，保存到dump.rdb文件中。可以通过SAVE（同步）或BGSAVE（异步fork子进程）触发。恢复时直接加载文件，速度很快，但可能丢失最后一次快照之后的数据。
>
> **AOF**是记录每一个写操作命令，保存到appendonly.aof文件中。有三种同步模式：always（每个命令都同步）、everysec（每秒同步，推荐）、no（依赖操作系统）。AOF可以做到数据更完整，但文件会比较大。Redis会定期重写AOF来压缩文件。
>
> 还有一种是Redis 4.0之后的混合模式，前半部分是RDB格式，后半部分是AOF格式，综合了两种方式的优点。实际使用中，我会根据业务对数据安全的要求来选择合适的持久化方式。

---

### 8. RDB和AOF的区别？如何选择？

#### 8.1 详细对比

| 对比项 | RDB | AOF |
|--------|-----|-----|
| 文件体积 | 小（压缩过） | 大（文本） |
| 恢复速度 | 快 | 慢 |
| 数据安全性 | 可能丢数据 | 可配置 |
| 写入方式 | 一次性全量 | 增量追加 |
| IO性能 | 好 | 一般 |
| 复杂度 | 简单 | 稍复杂 |

#### 8.2 场景选择

**用RDB的场景**：
- 对数据完整性要求不高
- 可以接受分钟级的数据丢失
- 主要追求性能

**用AOF的场景**：
- 对数据完整性要求高
- 不能接受数据丢失

**用混合模式的场景**：
- 追求极致的安全
- Redis 4.0+

```
我的生产配置（仅供参考）：

appendfsync everysec
rdbcompression yes
save 900 1  # 至少1个key变化，900秒后触发
save 300 10 # 至少10个key变化，300秒后触发

```

### 9. Redis是如何fork子进程的？

#### 9.1 什么是fork？

fork是Linux的一个系统调用，可以创建一个「子进程」：

```
主进程（父进程）
  ↓ fork()
子进程 ←→ 父子进程共享数据（刚fork时）
  ↓ 各自修改
独立的数据（Copy-on-Write）
```

#### 9.2 Copy-on-Write（写时复制）

这是理解RDB持久化的关键！

```
fork的瞬间：
┌─────────────────┐
│ 父进程的数据     │ ←→ 子进程共享同一个内存区域
│ [same physical] │
└─────────────────┘

只有当某一方要修改时：
┌─────────────────┐     ┌─────────────────┐
│ 父进程的数据     │     │ 子进程的副本     │
│ [modified]      │ ←→  │ [copy for child] │
└─────────────────┘     └─────────────────┘
```

**优点**：fork不需要复制整个内存，只需要复制「修改过的页面」！

#### 9.2 问题：fork会阻塞吗？

**答案是：会的！**

```
fork的痛点：
- 虽然用了写时复制，但fork本身需要遍历页表
- 数据量大时，fork会很慢
- 在fork期间，Redis会被阻塞住
```

**解决方案**：
```
1. 控制Redis的最大内存（不要太大）
2. 使用AOF而不是RDB
3. 降低fork频率
4. 硬件升级（SSD比HDD快很多）
```

## 第四章 缓存与性能 —— 如何正确使用Redis作为缓存？（高频 ★★★★★）

这是实际工作中最重要的一部分！面试必问！

### 10. Redis如何作为缓存使用？

#### 10.1 为什么要用缓存？

直接查数据库不行吗？

```
性能对比：
┌────────────────────────────────────────────┐
│ 数据库查询                         │ ~10ms    │
│ Redis查询                          │ ~0.1ms   │
│ 差距：100倍！                                     │
└────────────────────────────────────────────┘
```

所以要把「热点数据」放到Redis里，加速访问。

#### 10.2 缓存的基本模式

```
有缓存时：缓存 → 返回
无缓存时：
  1. 查数据库
  2. 写入Redis
  3. 返回

这叫做「Cache Aside」模式，是最常用的。
```

#### 10.3 五大缓存问题

接下来我们要详细讲：

1. 缓存穿透
2. 缓存击穿
3. 缓存雪崩
4. 缓存一致性
5. 缓存资源控制

### 11. 什么是缓存穿透？如何解决？

#### 11.1 概念

**缓存穿透**：一个数据，Redis缓存里没有，数据库里也没有。每次请求都穿透到数据库。

```
请求：查询 user:id=99999
  → Redis：无
  → 数据库：无
  → 返回：null
  → 完了，下次还穿透！穿透了！
```

**原因**：
- 恶意请求（故意查不存在的数据）
- 代码bug，查了一个不应该查的ID
- 初始数据就是空的

#### 11.2 危害

```
大量穿透请求 → 每次都查数据库
  → 数据库压力大
  → 可能被打挂
```

#### 11.3 解决方案

**方案1：空值缓存**

```
第一次穿透：
  查DB → 无
  写Redis：key="user:99999", value="null"，过期时间5分钟

下次请求：
  查Redis → 有 → 直接返回"null"
  → 不查DB
```

缺点：需要额外的内存存「空值」

**方案2：布隆过滤器（Bloom Filter）**

这是一个巧妙的数据结构！

```
原理：用一个数组，存「可能存在」或「肯定不存在」
       ┌─────────────┐
key1 → │ ✓ 存在    │ ← 判断key是否存在
key2 → │ ✗ 不存在  │
key3 → │ ? 可能    │ ← 有一定概率误判
       └─────────────┘

优点：节省内存（只占1.18MB，可以存1亿个key）
缺点：有误判率（约1%），可以接受
```

**方案3：前端校验**

- 参数校验
- 限流
- 黑名单

---

### 12. 什么是缓存击穿？如何解决？

#### 12.1 概念

**缓存击穿**：一个「热点」key，突然过期了！在过期的瞬间，大量请求同时穿透到数据库。

```
时间点：12:00:00（过期时间到）
  ┌──────────────────────────────────────────
  │ 请求A查Redis → 没数据 → 查DB → 写Redis   │
  │ 请求B查Redis → 没数据 → 查DB → 写Redis   │
  │ 请求C查Redis → 没数据 → 查DB → 写Redis   │
  │ ...                                   │
  │ 同时1000个请���，DB被打挂！
  └──────────────────────────────────────────
```

#### 12.2 解决方案

**方案1：互斥锁**

```
只有拿到锁的请求去查DB：
  ┌────────────────────
  │ 请求A → 抢锁成功 → 查DB → 写Redis → 放锁
  │ 请求B → 抢锁失败 → 等/重试
  │ 请求C → 抢锁失败 → 等/重试
  │ ...
  └────────────────────
```

实现：
```lua
-- Lua脚本：分布式锁
local lock = redis.call('SETNX', 'lock:update', '1')
if lock == 1 then
    -- 查DB
    -- 写Redis
    redis.call('DEL', 'lock:update')
    return 'done'
else
    return 'wait'
end
```

**方案2：逻辑过期（永不过期）**

```
不设置真正的过期时间：
- 数据放进去就不删
- 专门一个后台线程，定期刷新数据
- 或者数据变更时主动刷新
```

**方案3：双key**

```
存两份：
- key:v1 = 数据A（有过期时间）
- key:v2 = 数据A（无过期时间，作为备份）
过期时：查不到v1，就用v2，然后异步更新v1
```

### 13. 什么是缓存雪崩？如何解决？

#### 13.1 概念

**缓存雪崩**：大量缓存key，同时过期！或者Redis本身挂了！导致大量请求直接打到数据库。

```
时间点：整点！
  ┌──────────────────────────────────────
  │ 12:00:00 → 一大批key同时过期
  │ 请求A → Redis无 → DB
  │ 请求B → Redis无 → DB
  │ ...
  │ 10000个请求 → DB挂！
  └──────────────────────────────────────

还有一种情况：Redis集群整体故障
  ┌──────────────────────────────────────
  │ Redis主节点挂了
  │ 从节点还没来得及切换
  │ 全部请求 → DB → 挂！
  └──────────────────────────────────────
```

#### 13.2 解决方案

**方案1：过期时间加随机值**

```python
# 不要统一设置
expire = 3600 + random.randint(0, 3600)

# 分散开，不要同时过期
```

**方案2：多级缓存**

```
┌─────────────────┐
│ L1: 本地缓存     │ ← 首先查（内存map，没有网络开销）
│ L2: Redis缓存   │ ← 其次查
│ L3: 数据库      │ ← 最后查
└─────────────────┘

某个层级挂了，还有下一层撑着！
```

**方案3：高可用架构**

```
主从 + Sentinel/Cluster
  → 自动故障转移
  → 几乎不会全体阵亡
```

**方案4：服务熔限流**

```
流量限制（Hystrix/Sentinel）：
- 超过阈值 → 排队/拒绝
- 保护DB不死
- 虽然用户体验降级，但服务还在
```

**方案5：数据预热**

```
系统启动时：
  - 先把热点数据加载到Redis
  - 避免启动后的大量穿透
```

### 14. 如何保证Redis缓存和数据库一致性？

这是最复杂的问题！没有「完美方案」，只有「权衡」。

#### 14.1 基本模式：Cache Aside

```
读：
  Redis → 有 → 返回
       → 无 → 查DB → 写Redis → 返回

写：
  DB更新 → 删除Redis（不是更新！）
```

**为什么是「删除」而不是「更新」？**

```
❌ 更新方式（有并发问题）：
  请求A：B更新为"A"
  请求B：B更新为"B"  同时发生
  结果：不确定谁是最后的

✓ 删除方式（更安全）：
  请求A：删除缓存
  请求B：删除缓存  同时发生
  结���：下次都会重新加载，一致
```

#### 14.2 最终一致性问题

```
Timeline：
  12:00:00  用户A：B=1，B->=2
  12:00:01  Redis：B仍然=1  ← 不一致！
  12:00:02  用户B：B查询Redis，得到1（旧数据）
```

**这是正常的**！最终一致性：允许短暂的不一致，只要最终一致就行。

#### 14.3 强一致性方案

**方案1：延迟双删**

```
写：
  1. 更新DB
  2. 删除Redis
  3. 延迟500ms（等并发高峰期过去）
  4. 再次删除Redis
     → 确保并发的「读-处理-写」也清理掉
```

**方案2：订阅binlog**

```
MySQL → binlog → Canal → Redis更新
  → 完全异步
  → 几乎实时
  → 推荐
```

**方案3：分布式锁**

```
写之前：获取锁
  → 只能有一个请求在写
  → 其他等待
  → 最安全，但是性能差
```

#### 14.4 选择建议

```
- 绝大多数场景：Cache Aside + 延迟双删够了
- 强一致场景：分布式锁
- 高性能 + 强一致：binlog同步
```

## 第五章 内存管理与淘汰策略 —— 内存不够怎么办？

### 15. Redis有哪些内存淘汰策略？

#### 15.1 为什么需要淘汰策略？

```
Redis内存会满！因为：
  - 数据越来越多
  - 内存有上限
  - 满了就无法写入
```

所以需要「淘汰策略」来决定：内存不够时，淘汰哪些数据？

#### 15.2 八大淘汰策略

| 策略 | 全称 | 说明 |
|-----|------|-----|
| noeviction | 不淘汰 | 报错，返回错误（默认）|
| volatile-lru | 过期LRU | 只淘汰有TTL的，用LRU算法 |
| allkeys-lru | 全量LRU | 所有key都用LRU |
| volatile-lfu | 过期LFU | 只淘汰有TTL的，用LFU算法 |
| allkeys-lfu | 全量LFU | 所有key都用LFU |
| volatile-random | 随机过期 | 随机淘汰有TTL的 |
| allkeys-random | 随机全量 | 随机淘汰所有 |
| volatile-ttl | 最短TTL | 淘汰TTL最小的 |

#### 15.3 LRU vs LFU

**LRU（Least Recently Used）：最近最少使用**

```
例子：
  - 5分钟前看过A
  - 1分钟前看过B
  - 要淘汰一个 → 淘汰A（更久没用）

适合：热点集中的场景
```

**LFU（Least Frequently Used）：最不经常使用**

```
例子：
  - A被访问1000次
  - B被访问10次
  - 要淘汰一个 → 淘汰B（访问少）

适合：热点分散的场景
```

#### 15.4 近似LRU

**问题**：真正的LRU需要记录每次访问时间，性能差

**Redis的做法**：采样LRU
```
maxmemory-samples 5  ← 随机抽5个，选最老的淘汰
效果接近全量LRU，但性能好很多！
```

## 第六章 事务与Lua脚本

### 18. Redis事务是怎么实现的？

#### 18.1 三个命令

```
WATCH key       # 监控一个key，如果变动则事务失败
MULTI          # 开始事务
SET key value  # 加入队列，但不执行
GET key
EXEC/ DISCARD # 执行/放弃
```

#### 18.2 特点

**不是真正的事务**！

```
❌ 没有回滚
   - 如果第3条命令失败，第1、2条还是会执行
△ 没有隔离性
   - WATCH只是乐观锁
```

**WATCH的原理**：
```
1. WATCH key
2. 事务期间，key被其他客户端修改
3. EXEC → nil（整个事务失败）
4. 需要重试
```

#### 18.3 适合场景

- 批量操作
- 需要「检查-然后操作」的场景

### 20. 什么是Lua脚本？为什么使用Lua？

#### 20.1 Lua是什么？

一门轻量级脚本语言，可以在Redis服务端执行。

#### 20.2 为什么要用Lua？

**减少网络往返**：一条Lua脚本可以包含多条命令

```lua
-- 原来：3次网络往返
GET score
INCR score
GET score

-- 现在：1次往返
EVAL "local s=redis.call('GET','score'); ..."
```

**原子性**：整个脚本作为原子执行

```
中间不会被其他命令打断！
适合「检查-然后操作」的场景
```

#### 20.3 实际案例

```lua
-- 扣库存
local stock = redis.call('GET', KEYS[1])
if tonumber(stock) >= tonumber(ARGV[1]) then
    redis.call('DECRBY', KEYS[1], ARGV[1])
    return 'OK'
else
    return 'NO_STOCK'
end
```

## 第七章 分布式锁

### 21. 如何实现Redis分布式锁？

#### 21.1 基础版

```redis
SET lock_key unique_id NX EX 30
# 唯一的值（UUID），30秒过期
# 用完释放
DEL lock_key
```

**问题**：
- 过期时间不好确定
- 可能释放别人的锁（非原子）
- 不能自动续期

#### 21.2 进阶版：单个Lua脚本

```lua
-- 原子加锁
local lock = redis.call('SET', KEYS[1], ARGV[1], 'NX', 'EX', ARGV[2])
if lock then return 1 else return 0 end
```

#### 21.3 进阶版：释放锁

```lua
-- 释放：只有持有者才能释放
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
else
    return 0
end
```

#### 21.4 Watch Dog自动续期

```lua
-- 后台线程，每10秒检查
-- 如果持有锁，延期
```
